05 · Proven

The verification ladder

Being precise about what is actually established, because "the scaffold is done" and "the scaffold works" are different claims.

✓

Local logic is proven

20 tests · local Spark · 25.30s

Not smoke tests. They pin the arguments: that the filter runs before the dedupe so a corrupt copy can't resurrect over a good row; that an ingest-time tie breaks on event time so silver doesn't churn between identical runs; that the amount cap is inclusive so the single largest order isn't silently lost; that a day of only cancelled orders produces no row rather than a zero row.

✓

The generator's defects are asserted

tests/test_generate.py

The generator's contract is that it injects duplicates, late arrivals and nulls. A change that quietly removed one would leave the pipeline tested against nothing interesting — so the defects themselves are asserted, and one test runs generator and transform together to confirm what was injected is what gets removed.

✓

CI is green on a cold machine

GitHub Actions · 56s · both jobs passed

Lint + tests run on a fresh ubuntu runner with no credentials, which is what keeps the repo honest for anyone reading it cold. The bundle-validate job is wired up and currently skips with a notice, because no DATABRICKS_HOST secret is set.

06 · Decisions

The bits worth being able to defend out loud

The round is open-book and rewards narrating trade-offs. These are already in the code as comments, so they're rehearsable rather than improvised.

clean_events

Filter, then dedupe

If the dedupe ran first, a corrupt later copy would win its window and then be dropped by the filter — losing the good copy with it. Order is the whole correctness argument, and there's a test named after exactly that failure.

clean_events

Latest ingest wins

A re-delivery is more often a correction than an accident, so last-write-wins is the safer default. The tie-break on event time is what makes it deterministic when a source re-sends within the same millisecond.

daily_revenue

Group by event date

A late order belongs to the day it happened. The cost is real and gets said rather than hidden: yesterday's number can still move. late_orders is its own column precisely so a figure that moved is explainable instead of alarming.

ml_train

Register ≠ promote

Every run registers a version; the @champion alias only moves on a genuine improvement, and a tie keeps the incumbent. Conflating the two is how a worse model ships.

ml_train

Split without shuffling

It's a time series. A random split leaks the future into training and produces a validation score that can't be reproduced in production. The last 20% of days is the honest holdout.

job vs pipeline

Both, deliberately

The pipeline gives lineage, expectations and incremental refresh for free, and takes away control. Neither is right in general — it depends how much of the work is genuinely table-to-table. Having both deployed makes that a demonstration.
